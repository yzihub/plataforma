  <action>
Criar o arquivo `src/app/api/webhook/imoveis/route.ts` com exportação `POST` apenas. Não criar GET.

**Estrutura geral do handler (ordem obrigatória):**

1. **Auth (401)** — Extrair `Authorization` header. Se ausente ou sem prefixo "Bearer ", retornar 401. Comparar token contra `process.env.WEBHOOK_IMOVEIS_SECRET` usando `crypto.timingSafeEqual` (importar `crypto` do Node). Se igual a strings de comprimento diferente, retornar 401 imediatamente (timingSafeEqual lança se comprimentos diferentes — tratar com try/catch ou verificar comprimentos antes). Log `webhook.imoveis.auth_failed` level warn.

2. **Content-Type (415)** — Verificar se `request.headers.get("content-type")?.includes("application/json")`. Se não, retornar `{ ok: false, error: "unsupported_media_type" }` status 415.

3. **Parse JSON (400)** — `await req.json()` em try/catch. Se falhar: `{ ok: false, error: "malformed_json", message: "..." }` status 400.

4. **Validar `evento` (422)** — Deve ser uma das strings: `imovel.upsert`, `imovel.delete`, `imovel.unpublish`. Senão: `{ ok: false, error: "invalid_event", message: "...", details: { field: "evento", reason: "..." } }` status 422.

5. **Validar `tenant_id` (422)** — UUID v4 regex + presença na whitelist ALLOWED_TENANTS. Regex: `/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i`. Senão: `{ ok: false, error: "invalid_tenant", ... }` status 422.

6. **Validar `id_imovel` (422)** — String não vazia, comprimento ≤ 100 chars. Senão: `{ ok: false, error: "invalid_id_imovel", ... }` status 422.

7. **Para imovel.upsert: validar `data` (422)** — Deve existir e ser objeto (não array, não null). Senão: `{ ok: false, error: "missing_data", ... }` status 422.

8. **Para imovel.upsert: validar tipos dos campos conhecidos em `data` (422)** — Verificar apenas campos presentes. Tipos esperados:
   - `titulo_comercial`, `titulo_seo`, `descricao_imovel`, `tipo_de_imovel`, `finalidade`, `bairro`, `link_do_imovel`, `link_sanitizado`, `imagem_card`, `foto_principal`, `status_publicacao`, `status_operacional` → `typeof val === "string"` (string numérica como "525000" é inválida para numeric, mas esses são text)
   - `quartos`, `suites`, `vagas` → aceitar `string` OU `number` (converter para string antes de persistir)
   - `metragem`, `valor` → `typeof val === "number"` OBRIGATÓRIO. String numérica ("525000") deve retornar 422 com `{ ok: false, error: "invalid_field_type", message: "Campo 'valor' deve ser numérico.", details: { field: "data.valor", reason: "expected numeric, got string" } }`.
   - `metadata` → `typeof val === "object" && val !== null && !Array.isArray(val)`
   - Campos desconhecidos (não listados acima) → ignorar silenciosamente.
   - `_extras` dentro de `data` → ignorar silenciosamente.

9. **Executar ação via Supabase admin client:**

   **imovel.upsert:**
   - Construir objeto de upsert com apenas os campos presentes em `data` (não incluir campos ausentes — isso garante o merge parcial via COALESCE no Supabase).
   - Sempre incluir `tenant_id` (do envelope), `id_imovel` (do envelope), `updated_at: new Date().toISOString()`.
   - Para `quartos`, `suites`, `vagas`: `String(val)` antes de adicionar ao objeto.
   - Para `metadata`: se presente, usar query raw para jsonb merge. Porém o Supabase JS client com `.upsert()` não suporta `||` direto — usar a seguinte abordagem: incluir `metadata` no payload do upsert normalmente (o ON CONFLICT DO UPDATE vai substituir, não mesclar via `||`). Para v1, merge parcial de metadata significa que se `metadata` está ausente em `data`, preservamos o valor existente — o COALESCE cuida disso. Se `metadata` está presente no payload, usar `rpc` para merge jsonb: chamar `admin.rpc('merge_imovel_metadata', { p_tenant_id: tenant_id, p_id_imovel: id_imovel, p_metadata: data.metadata })` SE a RPC existir. Se a RPC não existir, usar o valor direto no upsert (substituição simples na v1 é aceitável como fallback). **Abordagem recomendada para v1:** Incluir `metadata` diretamente no payload do upsert, aceitar que o ON CONFLICT DO UPDATE vai substituir o jsonb inteiro para esse campo. Documentar em comentário que merge via `||` requer RPC ou trigger — a ser implementado em v2 se necessário. Isso é consistente com a nota do anti-escopo na spec.
   - Usar `.upsert(payload, { onConflict: 'tenant_id,id_imovel' }).select('id, created_at').single()`.
   - Determinar `created: boolean` comparando se o resultado tem `created_at` próximo de now() — **alternativa simpler:** usar `.upsert(...).select('id').single()` e verificar se houve insert via um segundo query `count`. Abordagem mais simples: fazer SELECT antes para checar existência, depois upsert. Ou: usar `.upsert(...)` e confiar no `status` retornado — o Supabase retorna 201 para insert e 200 para update. Usar `data` e `error` do resultado; `created` = verificar se o row foi recém criado via query `select count` antes do upsert.
   - **Abordagem definitiva para `created`:** Executar `select('id').eq('tenant_id', tenant_id).eq('id_imovel', id_imovel).maybeSingle()` ANTES do upsert. Se resultado null → `created = true`. Se resultado existente → `created = false`. Depois executar o upsert.
   - Resposta 200: `{ ok: true, action: "upserted", created: boolean, id_imovel, tenant_id, imovel_id: <uuid interno> }`.

   **imovel.delete:**
   - `.delete().eq('tenant_id', tenant_id).eq('id_imovel', id_imovel).select('id')`.
   - `found = (data?.length ?? 0) > 0`.
   - Resposta 200: `{ ok: true, action: "delete", found: boolean, id_imovel, tenant_id }`.
   - Nunca retornar 404.

   **imovel.unpublish:**
   - `.update({ status_publicacao: 'Despublicado', status_operacional: 'indisponivel', updated_at: new Date().toISOString() }).eq('tenant_id', tenant_id).eq('id_imovel', id_imovel).select('id')`.
   - `found = (data?.length ?? 0) > 0`.
   - Resposta 200: `{ ok: true, action: "unpublish", found: boolean, id_imovel, tenant_id }`.
   - Nunca retornar 404.

10. **Logs estruturados JSON** — Usar `console.log(JSON.stringify({...}))` com os campos:
    - `timestamp`: `new Date().toISOString()`
    - `level`: `"info"` | `"warn"` | `"error"`
    - `event`: conforme tabela da spec (ex: `"webhook.imoveis.received"` no início, `"webhook.imoveis.upserted"` no sucesso)
    - `tenant_id`, `id_imovel`, `evento`, `http_status`, `duration_ms`, `source` (do header `X-Source`), `error_code` (apenas em falhas), `trace_id`
    - `trace_id`: gerar no início do handler com `crypto.randomUUID()`
    - `duration_ms`: calcular `Date.now() - startTime`
    - NÃO logar `body` completo em nível info.

11. **trace_id em 5xx** — Retornar `trace_id` no body de respostas 500: `{ ok: false, error: "internal_error", trace_id }`.

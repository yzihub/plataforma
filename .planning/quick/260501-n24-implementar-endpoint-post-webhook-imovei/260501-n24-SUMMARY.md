# Phase quick-260501-n24 Plan 01: Implementar POST /webhook/imoveis Summary

**One-liner:** Endpoint POST /api/webhook/imoveis com bearer auth via timingSafeEqual, validacao completa em 6 camadas, handlers upsert/delete/unpublish contra Supabase admin client e logs JSON estruturados com trace_id.

## O que foi implementado

`src/app/api/webhook/imoveis/route.ts` — handler POST completo para receber eventos de imoveis do n8n e persistir no Supabase.

### Fluxo de validacao (em ordem)

1. **Auth 401** — Header `Authorization: Bearer <token>` comparado contra `WEBHOOK_IMOVEIS_SECRET` via `timingSafeEqual` (constant-time para evitar timing attack). Verifica comprimento antes da comparacao para evitar excecao do Node.
2. **Content-Type 415** — Rejeita qualquer Content-Type que nao seja `application/json`.
3. **JSON parse 400** — Try/catch em `request.json()` com mensagem de erro.
4. **evento 422** — Enum fechado: `imovel.upsert`, `imovel.delete`, `imovel.unpublish`.
5. **tenant_id 422** — UUID v4 regex + whitelist (Cafe com Pam + Jurema Brokers).
6. **id_imovel 422** — String nao vazia, max 100 chars.
7. **data 422** — Para upsert: objeto obrigatorio (nao null, nao array).
8. **tipos de campos 422** — text fields: string; quartos/suites/vagas: string ou number; metragem/valor: number obrigatorio (string numerica rejeitada); metadata: objeto.

### Handlers

**imovel.upsert:**
- SELECT before upsert para determinar `created: true/false`
- Payload construido com apenas os campos presentes em `data` (merge parcial — campos ausentes nao sao enviados, Supabase ON CONFLICT COALESCE os preserva)
- quartos/suites/vagas convertidos para String() antes de persistir
- metadata: merge client-side em JS (`{...existingMeta, ...incomingMeta}`), com remocao de chaves null (jsonb_strip_nulls equivalent)
- Resposta: `{ ok: true, action: "upserted", created: boolean, id_imovel, tenant_id, imovel_id: <uuid> }`

**imovel.delete:**
- Hard delete fisico `.delete().eq('tenant_id').eq('id_imovel').select('id')`
- Idempotente: `found = (data?.length ?? 0) > 0`
- Nunca retorna 404
- Resposta: `{ ok: true, action: "delete", found: boolean, id_imovel, tenant_id }`

**imovel.unpublish:**
- UPDATE: `status_publicacao = 'Despublicado'`, `status_operacional = 'indisponivel'`
- Idempotente: `found = (data?.length ?? 0) > 0`
- Nunca retorna 404
- Resposta: `{ ok: true, action: "unpublish", found: boolean, id_imovel, tenant_id }`

### Logs estruturados

JSON com 11 campos por request: `timestamp`, `level`, `event`, `tenant_id`, `id_imovel`, `evento`, `http_status`, `duration_ms`, `source` (de X-Source header), `error_code` (apenas em falhas), `trace_id`.

`trace_id` e gerado com `crypto.randomUUID()` no inicio do handler e retornado no body de respostas 500.

Payload completo nao e logado em nivel info.

## Casos de borda tratados

- Token ausente ou sem prefixo "Bearer " → 401 imediato
- Tokens de comprimento diferente → verificacao de length antes do timingSafeEqual (evita excecao do Node)
- `WEBHOOK_IMOVEIS_SECRET` nao configurada → token invalido (string vazia nao passa)
- `valor` como string numerica `"525000"` → 422 `invalid_field_type`
- `data` como array → 422 `missing_data`
- `metadata` como array → 422 `invalid_field_type`
- `imovel.delete` em imóvel inexistente → 200 `{ found: false }` (idempotente)
- `imovel.unpublish` em imovel inexistente → 200 `{ found: false }` (idempotente)
- Campos extras em `data` desconhecidos → ignorados silenciosamente
- `_extras` no envelope raiz → ignorado silenciosamente
- Erro de banco → 500 com `trace_id` no body
- metadata null explícito → limpa o campo no banco (nao faz merge)

## Env var necessaria

```
WEBHOOK_IMOVEIS_SECRET=<bearer_token_estatico_compartilhado_com_n8n>
```

Adicionar em `.env.local` (desenvolvimento) e nas env vars do Vercel (producao). **Nunca expor como `NEXT_PUBLIC_*`.**
